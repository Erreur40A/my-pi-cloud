# Authentication — V1 specification

## Scope

- Several users (family), open sign-up, LAN only (see [network](../network/spec.md)).
- No roles in V1: every user has the same rights over their own files.

## Accounts

- Users log in with their **email**. It is a `UNIQUE NOT NULL` column, not the primary key: the key is a UUID (see [database](../database/spec.md#ids)).
  - Why not the email as primary key: an address can change, and every table referencing the user (files, refresh tokens) would have to follow. The user id also goes into the JWT's `sub`, readable by anyone holding the token: an email there would leak personal data.
- Emails are stored **trimmed and lowercased**: `Alice@example.com` and `alice@example.com` are the same account.
- No "forgot password" in V1: the maintainer resets a forgotten password. Why: a reset link needs outbound email from a LAN-only Pi (SMTP provider, app password, expiring reset tokens), too much for a handful of family users.
- Table name: `users`. `user` is a reserved word in PostgreSQL (`SELECT user;` returns the current role).

## Passwords

- Hashed with **Argon2id** through Spring Security's `Argon2PasswordEncoder`.
- The encoder generates the salt and stores it, with its parameters, inside the encoded string (`$argon2id$v=19$m=…,t=…,p=…$<salt>$<hash>`): a single `password_hash` column, no salt to manage by hand.
- Why not SHA-256/SHA-512, even salted: they are built to be fast. A high-end GPU computes around 20 billion SHA-256 per second, enough to try every 8-character alphanumeric password in a few hours. Argon2id has a tunable time cost and a **memory cost** (tens of MB per attempt), which removes the GPU's advantage: from billions of attempts per second down to thousands.
- The salt makes identical passwords produce different hashes and makes precomputed tables (rainbow tables) useless.

## Tokens

| Token | Format | Lifetime | Stored server-side |
|---|---|---|---|
| Access | JWT, signed | 15 minutes | No |
| Refresh | Opaque UUID v4 | 30 days | Yes, as a SHA-256 hash |

### Access token (JWT)

- Claims: the user id (`sub`), `iat`, `exp`. Nothing confidential: a JWT is only base64-encoded, anyone holding it can read it. Its safety comes from the signature, which prevents any change.
- Signed with an **asymmetric key pair**; the header carries a `kid` identifying the key.
- Why asymmetric: with a single server, HS256 would have been enough. A key pair separates signing from verifying: only the authentication code holds the private key; any future component that needs to verify tokens gets the public key only, and a leak on its side cannot forge tokens. It was also chosen to learn it.

### Refresh token

- A UUID v4 generated by `UUID.randomUUID()`, which uses `SecureRandom`: 122 random bits. A non-cryptographic generator (`java.util.Random`) would make tokens predictable.
- Stored as a **SHA-256 hash**: a database leak exposes no usable token. A fast hash is fine here, unlike passwords: a password is chosen by a human and has likely candidates; a 122-bit random value has none, and brute-forcing it takes far longer than the age of the universe even at billions of attempts per second.
- **Rotation**: each refresh returns a new refresh token and invalidates the previous one.
- **Reuse detection**: a refresh token already used must never come back. If it does, two parties hold a copy (the user and a thief) and the server cannot tell which one is legitimate: it **revokes the whole token chain** of that login. Both are logged out; the user logs in again with their password, the thief is locked out.

### Logout

- Logout revokes the refresh token chain of **this device** only.
- "Log out all my devices" revokes every chain of the user. In V1.

## Signing key

- The private key is provided as a **Docker Compose secret**, mounted read-only at `/run/secrets/jwt_private_key`. It is never in the repo nor in an image; the host-side `secrets/` folder is git-ignored.
- Rejected:
  - the Pi's OS keyring: Ubuntu Server has no graphical session to unlock it at boot, and the container cannot see the host's keyring;
  - `RUN --mount=type=secret`: a build-time secret, gone once the image is built; the key is needed at runtime.
- **Normal rotation**: new key pair with a new `kid`; the old public key is kept for 15 minutes so access tokens in flight stay valid.
- **Leak**: new key pair, old public key removed immediately. Every access token becomes invalid and users log in again. Nothing else is lost.

## Token storage on clients

| Client | Storage |
|---|---|
| Web | Cookies `HttpOnly`, `Secure`, `SameSite=Lax` |
| Android | Android Keystore |
| Desktop | OS credential store (Secret Service on Linux, Credential Manager on Windows, Keychain on macOS), through the `keyring` crate |

- Environment variables were ruled out for the desktop: an app cannot create one that outlives its process (it would have to write the token in clear in a shell profile), and any process of the user can read them.

## Token transport

The server accepts two transports:

| Transport | Used by | Request | Response |
|---|---|---|---|
| Cookies | Web | Cookies sent by the browser | `Set-Cookie` |
| Header and body | Android, desktop, curl | `Authorization: Bearer <jwt>` (RFC 6750); refresh token in the body | Tokens in the body |

- **Login**: the client states which transport it wants (`cookie` or `body`). No token exists yet, so the server has nothing else to go on. Lying gains nothing: getting tokens takes the password, and an attacker who has it is already in.
- **Refresh**: the response goes back **through the channel the refresh token came in**, whatever the client states. Why: a malicious script in the page (XSS) cannot read the `HttpOnly` cookie, but the browser attaches it by itself. If the client could ask for `body`, the script would call the refresh endpoint and read fresh tokens from the response.
- **Both transports in one request** (a cookie and an `Authorization` header, or a refresh token in a cookie and in the body): `400`, with no side effect. No correct client sends both. Revoking anything would be wrong: the request is not proof of theft (a developer testing with curl can do it), and an access token does not say which refresh chain it belongs to.
- Guessing the client from `User-Agent` was rejected: free text that changes with every browser version, and a wrong guess hands tokens to page scripts.
- The `Authorization` header is not exposed to CSRF: a browser never adds it by itself.

## CSRF

- The browser sends cookies by itself, even on requests triggered by another site.
- `SameSite=Lax` sends the cookie on top-level navigations (`GET` when following a link) but not on cross-site `POST`, `PUT`, `DELETE`.
- **API rule: no `GET` ever changes state.** Without this rule, `Lax` protects nothing.
- Why not `Strict`: the web app and the API share one origin, so `Strict` would not block the app's own calls; it would only make a user following a link to the drive from an e-mail arrive logged out.

## Login rate limiting

Argon2id protects a leaked database; it does nothing against guessing passwords directly on the login endpoint.

- Counter per **(IP, account) pair**.
- After **3 failures**, wait **3 minutes**; the wait **doubles** on each further failure (3, 6, 12… minutes), capped at **1 day**.
- A successful login resets the counter of that pair.

Why the pair:

| Counter per | Problem |
|---|---|
| Account | An attacker fails on purpose and locks the victim out of their own account. |
| IP | Sign-up is open: an attacker logs into their own account from the same IP to reset the counter, then keeps guessing. |
| (IP, account) | The attacker's successes on their own account do not reset the pair targeting the victim, and the victim, on another IP, is never blocked. |

### Real client IP behind Nginx

Spring Boot sits behind Nginx: without configuration, every request comes from the Nginx container's IP, and rate limiting would block the whole family at once.

- Nginx forwards the client IP (`X-Forwarded-For` / `X-Real-IP`).
- Spring Boot trusts this header **only from the Nginx container**. Otherwise anyone could write any IP in it and escape the limit.

## Open

- JWT signing algorithm (RS256 or EdDSA).
- Where the rate-limit counters live (memory, lost on restart, or database).
- Password rules at sign-up.
- Cookie paths (e.g. the refresh cookie limited to the refresh endpoint).
